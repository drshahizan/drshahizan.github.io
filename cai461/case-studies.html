How the activity works

You have 8 minutes in a breakout room, then two groups share for 4 minutes. Your group delivers one slide or one chat message with five items.

Pick the case closest to your own project. Case A uses Contract Net from the Agent Interactions topic, Case B uses NetLogo from the ABMS topic, and Case C uses LLM agents from the Architectures lab.

Deliver these five items

  1. One metric from each of the four layers
  2. One baseline to compare against
  3. One experiment: what you vary, how many runs
  4. What you will trace or log
  5. One likely failure mode and how you would detect it

Case A: PNU Smart Shuttle

Eight electric shuttle agents serve ride requests across the PNU campus. When a student requests a ride, a dispatcher agent announces it with Contract Net; each shuttle bids its estimated pickup time, and the dispatcher awards the request to the best bid. Demand spikes sharply in the ten minutes between lectures.

What you know about the system

  • 8 shuttle agents and 1 dispatcher (manager).
  • Protocol: Contract Net, so 3 × 8 + 1 = 25 messages per request.
  • Peaks of around 50 requests in 5 minutes at class changes.
  • Shuttles can break down or go out of range.
Model answer: one possible evaluation plan

Use this after your group has tried. There is more than one good answer; what matters is that each choice is justified.

1. One metric per layer

LayerMetricWhy here
4 TrustRequests served in the same scenario across 5 repeated runs (pass^5), and requests left unserved after a shuttle failureStudents need the service to work every time, not on average.
3 Systemp95 time from request to award, and requests handled per minute at peakPeak load is when the protocol is most likely to break.
2 InteractionTotal passenger waiting time against an optimal assignment (social welfare), plus the longest single wait (egalitarian)Good average waits can hide a few students waiting very long.
1 AgentP(Ψ) where Ψ = picked up within 10 minutes of request (achievement) and never above seat capacity (maintenance)States the success predicate in Wooldridge’s terms.

2. Baseline

Greedy nearest-shuttle assignment, which needs only 2 messages per request, and random assignment as a floor.

3. Experiment

Vary request rate (10, 30, 50 per 5 minutes) and number of shuttles (4, 8, 16). Run each of the 9 settings 30 times with different seeds in a simulator, and repeat with one shuttle removed at minute 3. Report mean ± 95% CI and test Contract Net against greedy at each setting.

Worked example: the six experiment steps for Contract Net

StepElementExample for Contract Net
1Hypothesis“Contract Net completes tasks faster than random assignment for n ≥ 20.”
2VariablesIndependent: protocol, n. Dependent: latency, success rate. Controlled: task set, hardware.
3BaselineRandom, greedy, or a single agent.
4Repetitions30 runs per setting with different random seeds.
5StatisticsMean ± standard deviation or a 95% confidence interval, and a test of the difference.
6ReproducibilityPublish code, parameters, seeds and model versions.

4. What to trace or log

Use the request ID as the FIPA conversation-id. Log each CFP, bid (with the shuttle’s position and bid value), award, pickup and drop-off as spans with timestamps. Count messages per conversation with the JADE Sniffer.

5. Likely failure mode and how to detect it

A shuttle wins a request, then breaks down, and the request is never re-announced. Detect it by searching the traces for conversations that have an award span but no pickup span within 10 minutes. The fix is an award timeout that re-runs the auction.

Case B: Campus Evacuation Model

A NetLogo model simulates 3,000 students leaving teaching buildings during a fire drill. Each student agent walks towards an exit, slows down in crowds and may change exit if one is blocked. Campus safety wants to know whether the current exits are enough, and which exit to close for maintenance with least risk.

What you know about the system

  • 3,000 student agents, several buildings and exits.
  • Parameters: walking speed, exit width, share of students who know the nearest exit.
  • Campus safety recorded total evacuation times from two past drills.
  • Outputs are stochastic; every run differs.
Model answer: one possible evaluation plan

Use this after your group has tried. There is more than one good answer; what matters is that each choice is justified.

1. One metric per layer

LayerMetricWhy here
4 TrustError between simulated and recorded drill evacuation times (macro validation), and how much the result shifts when walking speed changes by 10%Decisions will be made from this model, so it must match reality and not hinge on one guessed value.
3 SystemTotal evacuation time, the time until the last student is out, at 1,000, 2,000 and 3,000 studentsThe curve shows when exits become the bottleneck.
2 InteractionMaximum queue length at each exit, and the ratio of selfish nearest-exit time to an optimised exit assignment (price of anarchy)Congestion is an emergent interaction, not a property of one agent.
1 AgentShare of agents that reach an exit (achievement) without entering a blocked corridor (maintenance)Checks that individual behaviour is right before trusting the totals.

2. Baseline

A simple flow estimate (students ÷ exit capacity per second) and the recorded times from the last real drill.

3. Experiment

In BehaviorSpace, vary blocked exits (none, one, two) and walking speed (1.0, 1.2, 1.4 m/s) with 30 repetitions: 3 × 3 × 30 = 270 runs. Report each setting as mean ± 95% CI. Document the model in ODD, stating under Observation exactly which outputs you record.

4. What to trace or log

Per tick: students evacuated through each exit and queue length per exit. Per agent: start position, chosen exit, exit changes and exit time. Store the random seed with every run.

5. Likely failure mode and how to detect it

All agents choose the same nearest exit and gridlock at one narrow door, which real people would avoid by switching. Detect it in verification with extreme values (for example one exit open) and by comparing the share of students per exit with the drill records; a large mismatch points to wrong micro-behaviour.

Case C: Course-Advising Crew

Three LLM agents answer students’ registration questions. A planner breaks the question down, a retriever searches the course catalogue and university regulations, and a checker verifies the draft answer before it is sent. During registration week it receives hundreds of questions a day.

What you know about the system

  • Planner, retriever and checker, each an LLM call with its own prompt.
  • Tools: catalogue search, regulations search.
  • Answers are free text, so correctness is hard to check automatically.
  • A wrong answer can make a student miss a prerequisite or deadline.
Model answer: one possible evaluation plan

Use this after your group has tried. There is more than one good answer; what matters is that each choice is justified.

1. One metric per layer

LayerMetricWhy here
4 Trustpass^3 per question, cost per correct answer, and the number of answers that state a rule not found in the regulationsStudents rely on it; a confident wrong answer is worse than no answer.
3 Systemp50 and p95 latency per question and tokens per question during a simulated registration-week loadLong waits and cost spikes appear only under load.
2 InteractionPlanner-retriever-checker turns per question, and how often the checker rejects a draft and the crew recoversShows whether the crew coordinates or just loops.
1 AgentCorrectness against the official rules: exact match for facts (dates, credit limits) and a rubric judge for explanationsSplits checkable facts from open-ended text.

2. Baseline

A single LLM with the same retrieval tools and no crew, and the existing static FAQ page.

3. Experiment

40 real registration questions with reference answers written by an advisor. Run each question 3 times with each design (crew against single agent), then compare the crew as a sequential chain against a supervisor (star). Validate the rubric judge on 30 human-labelled answers before trusting it.

4. What to trace or log

OpenTelemetry spans: invoke_agent for planner, retriever and checker; execute_tool for each search with the retrieved document IDs; chat spans with input and output tokens; and the checker’s verdict as an attribute.

5. Likely failure mode and how to detect it

The checker approves an answer that cites an outdated regulation (MAST: incorrect verification). Detect it with the judge’s grounding score and a weekly spot check of approved answers against the current regulations; the trace shows which document the retriever returned.

Lessons from published studies

Four real results that the lecture draws on. Each shows a layer that a narrow evaluation would have missed.

Consistency collapses with repetition

τ-bench (Yao et al., ICLR 2025). A GPT-4o function-calling agent solved about 61% of retail customer-service tasks on a single try, but fewer than 25% when the same task had to succeed in all 8 trials.

Layer missed: 4, reliability. Lesson: report pass^k, not only pass^1.

Accuracy without cost misleads

AI Agents That Matter (Kapoor et al., TMLR 2025). Complex agent designs reported as state of the art were often matched by simple baselines, such as retrying or majority voting, at a fraction of the cost.

Layer missed: 4, cost. Lesson: plot accuracy against cost and keep only the Pareto frontier.

Logs reveal what scores hide

Holistic Agent Leaderboard (Kapoor et al., ICLR 2026). Reading agent logs at scale uncovered agents searching for a benchmark’s answers online instead of solving the task, and misusing credit cards in flight-booking tasks.

Layer missed: 4, safety and policy. Lesson: trace everything and inspect the traces, not only the final score.

Failures come from design, not only the model

MAST (Cemri et al., NeurIPS 2025 D&B). Across seven open-source multi-agent frameworks, most failures traced back to specification and coordination problems: repeated steps, ignored stopping conditions, weak verification.

Layers missed: 2 and 4. Lesson: label failed traces with a taxonomy so you fix the cause, not the symptom.
