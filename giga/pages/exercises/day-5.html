SHARED CASE STUDY

Mersing Coastal Homestay

A fictional family-run homestay in Mersing, Johor, wants to present packages, receive enquiries and organise requests. Reuse the brochure and banner from Day 3, plus the page structure from Day 4.

Two different practice systems: Day 4 uses Google Sheets to save an enquiry and show a confirmation. Day 5 uses Supabase for a separate booking table and manager view. The 6,000 visitor sessions are analytics data; they are not imported as bookings.

Keep it fictional: the 6,000-row Day 4 file contains visit sessions, not bookings. Do not copy it into the booking table or enter real guest names, phone numbers, identity numbers, addresses or payment details.

0120 MINUTES

Map the visitor journey

Start from the Day 3 promotional kit and Day 4 static page. Decide what a visitor and a homestay manager need to do.

  1. Choose three fictional packages from the Day 3 brochure.
  2. Write the visitor flow: view packages → enter dates and party size → submit enquiry → see confirmation.
  3. Write the manager flow: sign in to the practice app → view requests → update status.
  4. Sketch the package page, enquiry form and manager list on paper.
SaveA one-page user-flow sketch and the selected Day 3 assets
0215 MINUTES

Open the training project

Use the included starter app and the isolated Supabase training project provided by the lecturer.

  1. Open the assigned project and starter folder.
  2. Open assets/js/config.js and locate the project URL and publishable key placeholders.
  3. Confirm the lecturer has provided the approved access policy and test sign-in instructions.
  4. Keep secret keys and real guest information out of browser code, AI prompts and public GitHub.
Before codingConfirm the starter app, demo access and reviewed RLS policy are available
0330 MINUTES

Create the booking table

Create one small table named booking_requests. Use field names that are easy to understand and test.

id · generated IDcreated_at · timestampcheck_in_date · datepackage_type · textguest_count · integervisitor_country · textchannel · textbooking_status · textbooking_value_rm · number
  1. Download and unzip the Day 5 starter kit.
  2. Open supabase/setup.sql and follow the lecturer’s setup instructions to create the table and reviewed training policies.
  3. Run supabase/seed-bookings.sql to add 12 fictional records.
  4. Compare the field names with the Day 4 Sheet. They serve separate practice apps and datasets.
DeliverA booking_requests table with fictional sample records
0425 MINUTES

Check who can access records

Read and test the policy supplied by the lecturer. Participants should not invent broad public access rules.

  1. Confirm Row Level Security (RLS) is enabled.
  2. Read which actions the practice account can perform.
  3. Sign in using the supplied demo flow, if required by the policy.
  4. Try one allowed action and one action that should be blocked; note the result.
Key ideaThe publishable key is used with RLS; secret keys must remain in a trusted server environment.
0560 MINUTES

Personalise the package page and connect the enquiry form

Use the runnable reference to see the target, then reuse the brochure style, banner and package descriptions from Day 3. Configure the connection and inspect how one form submission works.

  1. Show the three fictional packages with a short description and the Day 3 visual assets.
  2. Add fields for check-in date, package, guest count and visitor country.
  3. Validate required fields and sensible guest counts before submission.
  4. Enter the assigned project URL and publishable key in assets/js/config.js.
  5. Ask AI to explain the form submit handler before you change it.
  6. Submit a fictional request and confirm that the app shows a confirmation; the manager will verify the row after sign-in.
MilestoneA package page submits a simulated enquiry and shows a confirmation message
0660 MINUTES

Understand and customise the manager list

Use the reference list to see the expected result. Trace how a request is read, how its status is updated and how a test row is deleted.

  1. Ask AI to explain the loadBookings function and identify which query reads the table.
  2. Trace the status update and delete handlers in assets/js/app.js.
  3. Ask AI to change one small detail, such as the status label or table column order; review the change before keeping it.
  4. Show loading, success and error messages.
  5. Refresh the app and confirm a saved status change remains.
DeliverA manager screen that can read and manage practice requests
0730 MINUTES

Test and present the capstone

Demonstrate one end-to-end visitor request and explain how the manager handles it.

  1. Submit a request with valid values and show its confirmation.
  2. Check the saved row in Supabase and update its status.
  3. Try an empty date or invalid guest count and fix one issue.
  4. Test the visitor form while signed out: it should insert a Pending request but not display the manager list.
  5. Sign in with the lecturer-provided manager account; confirm the list loads, update a status and delete a test row.
  6. If a role is blocked, record the expected result and ask the lecturer to check the approved policy. Do not test only from the database admin screen.
  7. Present the service need, app flow, one limitation and one improvement needed before real deployment.

PROMPT 5.1 · USER JOURNEY

Plan the app screens

Act as a patient design tutor for a beginner. Help me plan a small booking app for the fictional Mersing Coastal Homestay. I already have a brochure and banner from Day 3 and a static page from Day 4. Create two user journeys: (1) visitor views three packages and submits an enquiry; (2) manager views requests and changes their status. List the screens, fields and buttons in order. Keep the scope small. Do not add payment, real contact details or features I did not request.

Expected output: a short screen list and a clear visitor-to-manager flow.

PROMPT 5.2 · TABLE DESIGN

Plan the database table

Act as a patient database tutor. Help me create one Supabase table named booking_requests for fictional training data. Use these fields: id (generated primary key), created_at, check_in_date, package_type, guest_count, visitor_country, channel, booking_status and booking_value_rm. Read the included setup.sql and seed-bookings.sql with me. Explain the fields and data types in plain English. Explain each table field and policy in beginner-friendly language. Do not generate replacement SQL or real personal information. The approved policy is for an isolated training project only.

Check: table fields match the app form and the separate Day 4 Sheet exercise.

PROMPT 5.3 · PACKAGE PAGE

Reuse the promotional design

Help me update my existing homestay website starter. Keep its current file structure. Add three package cards using only these approved fictional descriptions: [PASTE PACKAGE NAMES AND DESCRIPTIONS]. Reuse the Day 3 brochure/banner image files at these paths: [PASTE FILE PATHS]. Add an enquiry form with check_in_date, package_type, guest_count and visitor_country. Make the page responsive and accessible. Do not invent prices, facilities, contact details or availability. First explain which files you will change; then show the smallest changes needed.

Expected output: a package page that uses the participant’s own assets and a clear enquiry form.

PROMPT 5.4 · SUPABASE CONNECTION

Connect the enquiry form

I am a beginner using the instructor-provided Supabase JavaScript v2 starter app and an existing booking_requests table. Explain how to connect the form fields check_in_date, package_type, guest_count and visitor_country so that one fictional request is inserted and a confirmation message appears. Use placeholders for the project URL and publishable key. Never include a secret key. Use the existing RLS policy and sign-in flow without changing them. Ask me to paste the relevant starter code before suggesting edits. Make one small change at a time and tell me exactly which file and location to edit.

Milestone: one request appears in the app response and the Supabase table.

PROMPT 5.5 · ACCESS CHECK

Understand the RLS policy

Act as a database security tutor. Explain this lecturer-provided Row Level Security policy for my fictional booking_requests training table in plain English: [PASTE THE APPROVED POLICY]. Make a table showing which role can select, insert, update and delete, and what conditions apply. Do not rewrite the policy or recommend disabling RLS. Summarise the allowed and blocked actions. Do not claim the rule is tested until I have connected the app and tried it using the assigned test account.

Expected output: a plain-language access summary. Test permissions later through the connected app.

PROMPT 5.6 · MANAGER CRUD

Build the booking list actions

Using my existing starter files and booking_requests table, help me add a manager list that reads fictional booking rows, updates booking_status, and deletes a selected test row after confirmation. First inspect this code: [PASTE A SHORT EXCERPT WITH SECRETS REMOVED]. Keep the current files and layout. Use the lecturer-approved RLS policy and existing sign-in flow; do not disable RLS or add a broad public policy. Add loading, success and error messages. Explain and change one function at a time.

Expected output: manager can view requests and update or remove a test record.

PROMPT 5.7 · SAFE TROUBLESHOOTING

Understand one error

Explain this Supabase error in plain English for a beginner. First identify the likely cause and where to check it. Give one safe troubleshooting step at a time. Do not ask me for a secret key, password, private URL or real guest data. Do not recommend disabling RLS or putting a secret key in browser code. Error after removing secrets: [PASTE ERROR]. Relevant short code excerpt after removing secrets: [PASTE CODE].

Record: note the error, likely cause, fix and what happened after retesting.
